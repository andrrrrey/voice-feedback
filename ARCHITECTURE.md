# Voice Feedback Service — описание проекта и архитектуры

Этот документ объясняет, что делает сервис, как он устроен внутри и почему в
разработке приняты именно такие решения. Написано простым языком — так, чтобы
разобрался и новый разработчик, и человек без глубокого технического бэкграунда.

---

## 1. Что это за сервис и какую задачу он решает

**Voice Feedback Service** (он же «НейроОтзыв») — это веб-сервис для сбора
**голосовых отзывов** от клиентов компаний.

Идея простая. Клиенту бизнеса (например, кафе или салону) обычно лень писать
отзыв руками. Поэтому процесс упрощают до предела:

1. Клиент сканирует **QR-код** компании (его генерирует сервис) и попадает на
   красивую страницу-форму.
2. Нажимает большую кнопку микрофона и **наговаривает** отзыв голосом.
3. Нейросеть **распознаёт речь** и превращает её в текст, попутно **причёсывает**
   его (убирает «эээ», «ну», слова-паразиты, расставляет запятые) и
   **определяет тональность** (позитив / нейтрально / негатив).
4. Клиент при желании правит текст и нажимает «Отправить».
5. Готовый отзыв **уходит компании**: на e-mail, в CRM Bitrix24 и/или в
   мессенджер Max. А клиенту предлагают одним кликом разместить тот же текст на
   внешних площадках (Яндекс Карты, 2ГИС, Ozon, Wildberries) — текст уже
   автоматически скопирован в буфер обмена.

Управляет всем этим **админ-панель**: владелец сервиса создаёт компании,
загружает логотипы, настраивает интеграции и промпт для нейросети, просматривает
и выгружает отзывы.

В README проект честно помечен как **MVP** — то есть минимально жизнеспособный
продукт. Это объясняет многие архитектурные решения: ставка делается на скорость
разработки и простоту, а не на масштабируемость «на миллионы пользователей».

## 2. Технологический стек и почему именно он

| Технология | Зачем используется | Почему выбрана |
|---|---|---|
| **Python 3.10+** | Основной язык | Быстро писать, много готовых библиотек для работы с API и аудио |
| **FastAPI** | Веб-фреймворк (HTTP-сервер, маршруты, валидация) | Лёгкий, современный, умеет асинхронность, автоматически валидирует данные через Pydantic и сам генерирует документацию API |
| **SQLite + SQLAlchemy** | База данных + ORM | SQLite — это просто один файл, не нужно поднимать отдельный сервер БД. Идеально для MVP. SQLAlchemy позволяет работать с таблицами как с Python-объектами |
| **Jinja2** | Шаблоны HTML-страниц | Стандартный для Python способ генерировать HTML на сервере. Не нужен отдельный фронтенд-фреймворк |
| **qrcode + Pillow** | Генерация QR-кодов | Каждой компании нужен свой QR на её форму |
| **Яндекс SpeechKit** | Распознавание речи (Speech-to-Text) | Хорошо работает с русским языком |
| **YandexGPT** | Нормализация текста и оценка тональности | Российский LLM, удобно держать всё в одной Яндекс-экосистеме (один ключ, один folder) |
| **ffmpeg / ffprobe** | Конвертация и нарезка аудио | Браузеры пишут звук в разных форматах; их надо привести к тому, что понимает SpeechKit |
| **requests** | HTTP-запросы к внешним API | Простая синхронная библиотека для обращения к Яндексу, Bitrix, Max |
| **python-dotenv** | Чтение настроек из `.env` | Секреты (ключи, пароли) не хранятся в коде |
| **smtplib** (стандартная) | Отправка e-mail | Встроена в Python, не нужны зависимости |

Главная мысль выбора стека: **минимум инфраструктуры**. Весь сервис — это один
Python-процесс и один файл базы данных. Его можно запустить на самом простом
сервере.

## 3. Структура проекта (по файлам)

```
voice-feedback/
├── main.py            # Точка входа: все HTTP-маршруты (роуты) и склейка логики
├── database.py        # Подключение к SQLite, создание движка и сессий
├── models.py          # Таблицы БД (Company, Review) в виде классов SQLAlchemy
├── schemas.py         # Pydantic-схемы: проверка входных/выходных данных API
├── ai_utils.py        # Работа с Яндексом: распознавание речи + YandexGPT
├── email_utils.py     # Отправка отзыва на e-mail компании
├── bitrix_utils.py    # Создание лида в CRM Bitrix24
├── max_utils.py       # Интеграция с мессенджером Max (бот + long polling)
├── requirements.txt   # Список зависимостей
├── README.md          # Краткая инструкция по запуску
└── templates/         # HTML-страницы (Jinja2)
    ├── public_form.html      # Публичная форма для клиента (запись голоса)
    ├── admin_login.html      # Вход в админку
    ├── admin_dashboard.html  # Главная админка (управление компаниями)
    └── company_reviews.html  # Страница со списком отзывов компании
```

Логика разбита по принципу **«один файл — одна зона ответственности»**:
интеграция с каждым внешним сервисом живёт в отдельном `*_utils.py`. Это удобно:
если завтра e-mail заменят на что-то другое, трогать придётся только
`email_utils.py`, а не весь проект.

## 4. Модель данных

В базе всего **две таблицы** — этого достаточно для задачи.

### Company (компания)
Файл: `models.py`

Хранит всё про клиента сервиса:
- `name`, `slug`, `email` — название, кусок URL (`/r/{slug}`) и куда слать отзывы;
- `logo_path`, `qr_path` — пути к загруженному логотипу и сгенерированному QR;
- `prompt` — **индивидуальный** промпт для нейросети (можно настроить под
  конкретную компанию);
- `yandex_url`, `twogis_url`, `ozon_url`, `wildberries_url` — ссылки на карточки
  компании на внешних площадках (куда предлагать клиенту переслать отзыв);
- `bitrix_webhook_url`, `bitrix_source_label` — настройки интеграции с Bitrix24;
- `max_chat_id` — куда слать отзыв в мессенджере Max;
- `disable_email` — флаг «не отправлять на e-mail» (если компания пользуется
  только CRM/мессенджером).

### Review (отзыв)
Связан с компанией через `company_id`:
- `user_name` — имя клиента (необязательно);
- `audio_path` — путь к сохранённому аудиофайлу (для истории);
- `raw_text` — **как распознали** (сырой текст от SpeechKit);
- `normalized_text` — **после обработки** YandexGPT (или после ручной правки);
- `sentiment` — тональность: `positive` / `neutral` / `negative`;
- `status` — этап жизни отзыва: `draft` → `final` → `sent`.

**Почему два поля текста (raw и normalized)?** Чтобы ничего не терять. Сырой
текст остаётся как «первоисточник», а обработанный можно править. Если нейросеть
сработала плохо, всегда видно, что было на самом деле сказано.

**Почему статусы?** Отзыв проходит путь: сначала черновик (`draft`, сразу после
записи), потом финал после редактирования клиентом (`final`), потом отправлен
(`sent`). Это помогает понимать состояние записи.

## 5. Как устроена база данных и «мягкие миграции»

В `database.py` всё максимально просто: SQLite-файл `voice_feedback.db`,
`check_same_thread=False` (чтобы к БД можно было обращаться из разных потоков —
это важно из-за фонового потока Max-бота).

Интересное решение в `main.py` — **«мягкая миграция»**:

```python
Base.metadata.create_all(bind=engine)   # создаёт таблицы, если их ещё нет

# затем вручную добавляем недостающие колонки
inspector = inspect(conn)
columns = [col["name"] for col in inspector.get_columns("companies")]
if "prompt" not in columns:
    conn.execute(text("ALTER TABLE companies ADD COLUMN prompt TEXT"))
# ... и так для каждой новой колонки
```

**Что это и зачем.** Когда в проект добавляют новое поле компании (например,
`max_chat_id`), у уже существующей базы этой колонки нет. В «больших» проектах
для этого используют систему миграций (Alembic, он даже есть в зависимостях). Но
здесь автор пошёл проще: при каждом запуске код проверяет, есть ли нужные
колонки, и если нет — добавляет их «на лету».

**Почему так сделано.** Для MVP это прагматично: не нужно писать и прогонять
миграции, база сама «дорастает» до актуальной схемы при обновлении кода. Минус —
такой подход не масштабируется и не отслеживает историю изменений, поэтому для
зрелого продукта его стоит заменить на нормальный Alembic.

## 6. Главный сценарий: путь голосового отзыва

Это сердце сервиса. Разберём по шагам, что происходит «под капотом».

### Шаг 1. Клиент открывает форму
`GET /r/{company_slug}` → находит компанию по `slug` → отдаёт
`public_form.html` с данными компании (логотип, название, ссылки на площадки).

### Шаг 2. Запись голоса в браузере
Вся запись происходит на **стороне клиента** в JavaScript (`public_form.html`):

- Сначала пробуется современный **`MediaRecorder`**. Код старается записать сразу
  в `audio/ogg;codecs=opus` (лучший вариант для SpeechKit), иначе — в `webm`.
- Если браузер старый и `MediaRecorder` нет (актуально для некоторых iOS/Safari),
  включается **fallback на Web Audio API**: звук собирается вручную и
  упаковывается в `WAV` прямо в браузере (функция `encodeWAV`).

**Почему такая сложность.** Браузеры очень по-разному поддерживают запись звука.
Чтобы форма работала «у всех», заложено несколько путей: предпочтительный формат,
запасной формат и аварийный ручной режим. Это типичная защита от
фрагментированности браузеров.

### Шаг 3. Загрузка аудио и распознавание
`POST /api/public/{company_slug}/upload-audio` (в `main.py`):

1. Файл сохраняется как есть (для истории).
2. Определяется формат. Если это **не** ogg — вызывается **ffmpeg** и звук
   конвертируется в `ogg/opus` (моно, 48 кГц) — именно такой формат ждёт
   SpeechKit.
3. `transcribe_audio_with_speechkit()` отправляет аудио в **Яндекс SpeechKit** и
   получает сырой текст.
4. `normalize_and_analyze_with_yandex_gpt()` отправляет этот текст в
   **YandexGPT**, который возвращает причёсанный текст + тональность.
5. Создаётся `Review` со статусом `draft`, клиенту возвращается готовый текст.

**Важная деталь — нарезка длинного аудио.** SpeechKit в синхронном режиме
ограничен по длине. Поэтому в `ai_utils.py`:
- `ffprobe` измеряет длительность записи;
- если она больше 15 секунд, ffmpeg режет аудио на 15-секундные сегменты
  (`_transcribe_long_audio`), каждый распознаётся отдельно, а результаты
  склеиваются по порядку.

Это аккуратный обход ограничения дешёвого синхронного API, без перехода на более
сложный асинхронный режим распознавания.

### Шаг 4. Обработка текста нейросетью (YandexGPT)
Тут несколько продуманных решений (`ai_utils.py`):

- В модель одним промптом отправляются сразу **две задачи**: переписать отзыв и
  оценить тональность. Ответ просится строго в виде **JSON**
  (`{"normalized_text": ..., "sentiment": ...}`).
- Промпт нормализации можно настраивать: глобально через файл
  `normalization_prompt.txt` или индивидуально для компании (`company.prompt`).
- **Защита от «капризов» модели.** LLM иногда возвращает не чистый JSON, а текст с
  пояснениями. Поэтому `_parse_gpt_response` сначала пытается выдернуть JSON
  регуляркой `\{.*\}`, и только если совсем не вышло — переходит к запасному
  плану.
- **Запасная эвристика тональности** (`_heuristic_sentiment_from_text`). Если
  модель недоступна или вернула мусор, тональность определяется по **спискам
  слов-маркеров**: «не рекоменд», «ужасн», «хамств» → негатив; «отличн»,
  «рекомендую», «спасибо» → позитив. Причём **негатив приоритетнее**: если в
  тексте есть и плохое, и хорошее, ставится `negative`.

**Почему столько подстраховок.** Сервис общается с клиентом в реальном времени.
Если внешний AI «упал» или закапризничал, форма **не должна сломаться**. Лучше
показать чуть менее качественный текст и приблизительную тональность, чем ошибку.
Это принцип **graceful degradation** — «плавной деградации»: при сбое сервис
продолжает работать с урезанным качеством.

### Шаг 5. Финализация и рассылка
`POST /api/public/reviews/{review_id}/finalize`:

1. Сохраняет финальный (возможно, отредактированный) текст, статус → `final`.
2. Если e-mail не отключён — отправляет письмо (`send_review_email`). При успехе
   статус → `sent`.
3. Если настроен Bitrix24 — создаёт лид в CRM.
4. Если настроен Max — отправляет отзыв в мессенджер.

Все три канала **независимы**: каждый срабатывает, только если для компании
заданы соответствующие настройки. Результат по каждому каналу возвращается
клиенту (`email_sent`, `bitrix_lead_created`, `max_sent`).

**Почему доставка не блокирующая и «best-effort».** Если, скажем, Bitrix недоступен,
это не должно мешать отправке письма. Поэтому каждый канал обёрнут в свою
проверку и обработку ошибок, и сбой одного не валит остальные.

## 7. Внешние интеграции — почему так

### E-mail (`email_utils.py`)
Отправка через `smtplib` по SSL. Заложен **повтор попыток** (3 раза с паузой):
почтовые серверы иногда «моргают», и одна неудачная попытка ещё ничего не значит.
Настройки берутся из `.env` (по умолчанию заточено под Яндекс.Почту).

### Bitrix24 (`bitrix_utils.py`)
Создаёт лид через «входящий webhook» — это самый простой способ интеграции с
Bitrix, не требующий OAuth и приложений. Компании достаточно вставить один URL в
настройках. Тональность переводится на русский («Позитивный» и т.д.) для
наглядности в CRM.

### Max-мессенджер (`max_utils.py`)
Самая хитрая интеграция. Схема такая:
1. Админ запускает бота в Max → бот через **long polling** ловит это событие и
   отвечает «секретным ключом» (это `user_id` админа в Max).
2. Админ вставляет этот ключ в настройки компании (`max_chat_id`).
3. При финализации отзыв уходит этому пользователю.

Технически интересно, что бот работает в **отдельном фоновом потоке-демоне**
(`threading.Thread(daemon=True)`), запускается на старте приложения
(`@app.on_event("startup")`) и крутит цикл long polling. Поток помечен `daemon`,
чтобы он не мешал приложению завершаться.

**Почему отдельный поток, а не отдельный сервис.** Опять же — простота MVP. Не
нужно поднимать ещё один процесс или очередь; бот живёт внутри того же
веб-приложения. Для небольшой нагрузки этого достаточно.

## 8. Фронтенд: почему server-side рендеринг и «толстый» HTML

Отдельного фронтенд-приложения (React/Vue) **нет намеренно**. Страницы — это
Jinja2-шаблоны, которые сервер отдаёт сразу с данными. Вся интерактивность
(запись звука, отправка, копирование текста) написана на **чистом JavaScript**
прямо внутри HTML.

**Почему так:**
- Меньше технологий — быстрее разработка и проще деплой (нет отдельной сборки
  фронта).
- Публичная форма — это по сути одна страница; городить под неё SPA-фреймворк
  избыточно.
- Стили и скрипты лежат прямо в шаблоне — всё, что касается одной страницы, в
  одном месте.

Минусы тоже есть: HTML-файлы получились большими (форма ~900 строк, админка ~900
строк), CSS и JS дублируются между страницами. Для MVP это приемлемый компромисс,
но при росте проекта стоит вынести общие стили/скрипты в отдельные файлы.

Заметная деталь: повсюду используется префикс пути `/voice-feedback` (например,
`/voice-feedback/static/...`). Это значит, что сервис **развёрнут не в корне
домена**, а в подпути (за обратным прокси). Поэтому ссылки и QR-коды строятся с
учётом этого префикса (`https://dev.futuguru.com/voice-feedback/r/{slug}`).

## 9. Админ-панель и безопасность

Вход в админку (`admin_login.html`) проверяет логин/пароль из переменных
окружения (`ADMIN_LOGIN` / `ADMIN_PASSWORD`, по умолчанию `admin/admin123`). При
успехе ставится **простая кука** `admin_auth=1`, а каждый админский запрос
проверяет её через `require_admin()`.

Через админку можно: создавать/редактировать/удалять компании, грузить логотипы,
настраивать промпт (глобальный и для компании), ссылки на площадки, интеграции
Bitrix/Max, включать/выключать e-mail, смотреть отзывы и **выгружать их в CSV**.

**Честно о безопасности.** Текущая авторизация — намеренно примитивная (для MVP):
- кука `admin_auth=1` не подписана, её легко подделать;
- API-эндпоинты `/api/admin/...` (создание/удаление компаний) **не защищены**
  проверкой `require_admin` — защищены только HTML-страницы;
- логин/пароль и многие секреты имеют небезопасные значения по умолчанию.

Для реального продакшена это первое, что нужно усилить: подписанные сессии/JWT,
защита всех админских роутов, обязательная смена дефолтных паролей.

## 10. Конфигурация и секреты

Всё настраиваемое вынесено в **переменные окружения** (`.env`, читается через
`python-dotenv`): ключи Яндекса (`YANDEX_API_KEY`, `YANDEX_FOLDER_ID`), модель
GPT, промпты, SMTP-доступы, токен Max-бота, логин/пароль админа.

**Почему через `.env`.** Секреты не должны попадать в репозиторий и должны легко
меняться между окружениями (локально / тест / прод) без правки кода. Это
стандартная и правильная практика, выдержанная по всему проекту.

Промпт нормализации дополнительно кэшируется в памяти и хранится в файле
`normalization_prompt.txt` — чтобы изменения из админки переживали перезапуск, но
при этом не лезть лишний раз на диск (есть `_cached_normalization_prompt`).

## 11. Итог: сильные стороны и зоны роста

**Что сделано хорошо (и почему это правильно для MVP):**
- Чёткое разделение по файлам — каждая интеграция изолирована.
- Множество подстраховок вокруг ненадёжных внешних сервисов (повторы e-mail,
  fallback тональности, нарезка длинного аудио, запасные форматы записи в
  браузере) — сервис устойчив к сбоям.
- Минимум инфраструктуры: один процесс + файл БД, легко запускать и
  разворачивать.
- Гибкая настройка под каждую компанию (свой промпт, свои каналы доставки, свои
  площадки).

**Что стоит улучшить при взрослении продукта:**
- Заменить «мягкие миграции» на Alembic (он уже в зависимостях).
- Усилить авторизацию админки и защитить все `/api/admin` роуты.
- Перейти с SQLite на полноценную СУБД (PostgreSQL) при росте нагрузки.
- Вынести общие CSS/JS из шаблонов, уменьшить дублирование.
- Тяжёлые операции (распознавание, рассылку) при росте — увести в фоновую
  очередь задач, а не выполнять в момент HTTP-запроса.

Эти компромиссы — не недосмотр, а осознанный выбор в пользу скорости запуска.
Для MVP такая архитектура полностью оправдана: она простая, понятная и делает
ровно то, что нужно бизнесу.
